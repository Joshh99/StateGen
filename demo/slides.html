The Problem with One-Shot Code Generation

❌ Single shot fails

One LLM call generates the whole program. Any small error means the entire output is wrong — no recovery possible.

⚠ Global retry is wasteful

Regenerate the entire solution on every failure. Wastes tokens rewriting code that was already correct.

✓ Local repair is better

Identify which part failed. Repair only that part and leave the rest intact.


Real programs have natural structure: imports → helpers → main function.
We exploit this structure to make repair local and efficient.

Framing Code Generation as an MDP

MDP ComponentIn StateGen
State sPartial program built so far
Action aGenerate code for the next state
TransitionAppend fragment → new partial program
Reward+1 if all tests pass, 0 otherwise
BacktrackFailed state → retry or revert

Why local backtracking?

  • A bug in state i almost never comes from state i−1
  • Full MDP backtracking to s₀ wastes all prior work
  • Local retry = fix only the failing fragment
  • Empirically 2× better than full backtrack

Four Methods We Compare

Direct Gen

Single LLM call. No planning, no retry. Baseline floor.


1 LLM call

Self-Planning

Write a numbered plan first, then generate code from the plan. Retry whole solution on failure.


2+ LLM calls

Self-Debugging

Generate → explain the code in prose → repair based on explanation. (Chen et al., ICLR 2024)


3+ LLM calls

StateGen

Decompose into states → per-state verify & repair → final BCB eval.


2+ LLM calls

Step 1: Decomposition

One LLM call produces a structured breakdown of the problem:

STATE 0
Description: Import necessary modules and define constants.
Preconditions: none
Postconditions: 'pandas' in dir(); 'numpy' in dir()
CODE:
import pandas as pd
import numpy as np
END_STATE

STATE 1
Description: Define the main task_func that processes the dataframe.
Preconditions: pd, np
Postconditions: callable(task_func)
CODE:
def task_func(df, col):
    ...
END_STATE

Each state has preconditions (what must exist) and postconditions (structural assertions to verify output).

On failure → local repair

  • Error message passed back to LLM
  • LLM rewrites only the failing fragment
  • Previous states untouched
  • Up to 3 repair attempts per state

What quick check catches

  • Syntax errors (SyntaxError, IndentationError)
  • Import errors (missing modules)
  • Runtime crashes at definition time
  • Structural postconditions (callable(f))

Memory Manager

StateGen caches successful state → code mappings using sentence embeddings:

How it works

  • Key: (state description + context signature)
  • Value: code that passed quick check
  • Similarity threshold: 0.85 cosine similarity
  • On cache hit: skip LLM call entirely

In practice

  • 48 patterns cached across 148 tasks
  • State 0 (imports) reused most often
  • ~0.32 reuse rate across the benchmark

Example cache hit

"Import pandas, numpy, sklearn"
→ seen before at similarity 0.91
→ return cached import block
→ 0 LLM tokens used


Ablation: removing memory drops pass@1 from 29.7% → 28.4% (−1.3 pp) on DeepSeek.

⚠ MDP insight: Full backtrack is theoretically purer but empirically worse

A bug in state 2 almost never originates in state 0. Resetting to state 0 wastes tokens on code that was already correct. Local repair (retry only the failing state) is a better practical approximation.

Finding: stronger models favor simpler methods

For GPT-4o and Gemini, Self-Planning (~28-30%) matches or beats StateGen — the models are capable enough that the decomposition overhead isn't needed. StateGen's advantage is clearest on mid-tier models like DeepSeek-Coder.
